### ★ 本轮最有价值的产出：4 处设计冲突修正（文档 §2，勿遗忘）
- **C1 白名单 vs 全匿名**：破坏匿名的是**投票交易的 sender**，不是白名单本身。
  → 两段式准入：登记期录 `whitelist[addr]=commitment`；投票期 ZK 证明 + **交易由 Relayer 代发**。**Relayer 是全匿名的必要条件，不是优化项。**
- **C2 链上锁票**：公开链 storage 可直读，UI 隐藏≠隐私。
  → 必须「承诺—揭示」两层：投票期只存 `Poseidon(mask,salt)`；揭示期验哈希后累计。
  关键论证：N4 的防护目标是防跟风，该风险**只在投票期成立**，揭示期渐进公开无风险 → 自洽。
- **C3 合约签名**：EVM 合约无私钥，**无法签名**。等价物＝`resultHash` 锚定 + 独立复算（view 接口 + 脚本），成本极低。L2（观察员 EIP-712 签名）信任模型不同，不推荐。
- **C4 暂停权冲突**：v1 的 `PAUSER_ROLE` 与 N3 直接冲突 → **完全移除暂停接口**，阶段仅由 `block.timestamp` 推导。

### 架构关键点
- 合约：`ProposalFactory` + **一提案一 `Proposal` 实例** + `VoterRegistry` + `SemaphoreVerifier` + `MinimalForwarder`(ERC-2771)。命名由 Election 改为 Proposal。
- 四阶段状态机：`REGISTRATION → VOTING → REVEAL → FINALIZED`（+`revealEnd`），参数全部不可变。
- 多选：`uint16` 位图。**隐选项的代价**——投票期看不到位图，`maxChoices` 只能在揭示期校验，违规票作废（计入 `revealedUnused` 并公示）。
- 信任模型：唯一需信任管理员的是「名册准确性」，且全程上链留痕。
- 不变量 INV-1~INV-7（新增：阶段单调、名册冻结）。
- 风险新增 R13 Relayer 审查 / R14 揭示期弃权 / R16 登记权滥用。
- 单票合计 gas 约 300k–420k（投票 250–350k + 揭示 50–80k）。
- 实施 P1~P14；相对 v1 工期约 +25%~+35%。

### ★ 评审最重要的发现：F-02（严重，凭空造票）
原 `reveal()` 校验链只有「哈希匹配 + 未揭示 + popcount 合规」三项，**全部可由攻击者自造数据满足**：
攻击者任选 `mask/salt` → 自算 `Poseidon(mask,salt)` → 直接揭示 → **无限造票**，名册准入与 ZK 凭证全部失效。
**修复**：投票期写 `_commitmentCast[commitment]=true`，揭示期首行校验 `CommitmentNotCast()`。→ 新增 INV-8 + R17。
**通用教训（已写入报告 §5）**：设计文档通过评审 ≠ 实现安全。必须专项复核三类路径：
① 每个 mapping 写入是否有前置存在性/合法性校验；② calldata 输入是否都经链上验证；③ 批量循环中单条失败是否影响整批/可否反复触发。

### 其余 20 项（高 5 / 中 8 / 低 7）
- F-01 `phase()` 空档期返回 REGISTRATION → 名册锁定后仍可登记，破 INV-7。修：加 `IDLE`/`CLOSED` + **registerVoters 禁用 phase()**。
- F-03/F-04 `castVote` 参数冗余且 `uint256[8]` 类型不成立 → 改为单一 `ZKProof{merkleTreeRoot,nullifier,message,scope,points[8]}`，nullifier/message 只从 proof 读。
- F-05 `_nullifierUsed` 写入时点未约束 → 可在 verifyProof 前写脏状态 DoS 合法选民。修：G8 明确顺序 + INV-9。
- F-06 缺 `frozenRoot` 固化触发函数 → 新增无权限 `freezeVotersRoot()`（幂等）。
- F-07 INV-1 无计数器 → 加 `totalMarks`。
- F-08 揭示失败票无法标记可无限重试 → `RevealStatus{NONE,ACCEPTED,REJECTED}`。
- F-09 登记 gas 低估 3–4 倍（实为 60–100k/地址）→ 单批 ≤ 50 地址（原写 200）。
- F-10 EIP-712 必须绑定 `to` + `keccak256(data)` + `deadline`，否则跨 calldata/跨提案重放。
- F-11 匿名性质是「不可链接到真实身份」（假名性），**不得对外称「完全匿名」**——链上 `nullifier ↔ 选项` 关联可见。
- F-13 Q8 补贴若经 Relayer 代发 reveal 会泄露明文 → 改事后报销（与 Q12 一致）。
- F-17 揭示率 95% 是**监控指标非可回退项**（延长窗口与 N3 冲突）→ AS-17。
- F-21 `BallotCodec.validate` 的 `optionCount >= 16` off-by-one。

### ★ 实测踩坑（三个，均可复用）
1. **TS 7 与 ts-node 10 不兼容** → `hardhat compile` 崩在 `Cannot read properties of undefined (reading 'fileExists')`。
   根因：`hardhat-toolbox@5` 未限制 typescript 上限，npm 拉到 **7.0.2**，TS 7 移除了 ts-node 依赖的 `ts.sys`。
   **修复：显式 `npm i -D typescript@5.6.3`**。已定为【硬约束 5】——否则任何新环境都会复现。
2. **ethers v6 的 view 返回值是只读 Proxy** → 直接作为数组实参回传报
   `Cannot assign to read only property '0' of object '[object Array]'`。
   修复：`Array.from(await h.decode(...)).map(Boolean)`。链式调用（P3/P10 前端与索引器）必踩。
3. **Git Bash 下 `taskkill //F //PID` 参数被路径转换破坏** → 报「无效参数/选项 - '//F'」。
   改用 PowerShell 按端口杀：`Get-NetTCPConnection -LocalPort <P> -State Listen | Stop-Process -Force`。

→ **P8 部署顺序：PoseidonT3 库 → 业务合约（传 libraries）→ 验证时一并提供库地址。**

### ★ 关键 API 发现（对 P3 是决定性简化）
本版本 LeanIMT **不提供 generateProof / verifyProof**。
⇒ 成员证明**链下生成**、由 **ZK 电路校验**；合约只需比对 `proof.merkleTreeRoot == frozenRoot`，

64 叶(depth6) 59,198｜512 叶(depth9) 57,871｜2048 叶(depth11) 58,496 gas/叶 → **比值 0.99x（平坦）**。

### ★★★ 本阶段最重要的技术事实（照抄上游，否则全盘失效）
Semaphore 官方 `Semaphore.sol` 的公开信号构造：
```
[merkleTreeRoot, nullifier, _hash(message), _hash(scope)]
_hash(x) = uint256(keccak256(abi.encodePacked(x))) >> 8
```
- **message 与 scope 都要先哈希再入电路**；直接传原值 ⇒ 所有合法证明被拒。
- `merkleTreeDepth` 是**独立参数**，不在 pubSignals 内。
- `points[8]` 拆包顺序固定：0-1→pA，2-3/4-5→pB，6-7→pC。
**这三类错误在本机不产生任何报错**（无法生成合法证明来发现），只有真机才会暴露为「所有人都投不了票」。

### 应对：把无法验证的约束变成可断言的测试
1. `_hash` 由 private 改 internal，经 `ProposalHarness.hashScalar()` 暴露，与 JS 参考实现逐值比对。
2. **strictMode 替身**：`MockVerifier` 按上游公式**自行重算** hash 后逐项比对 pubSignals ——
   漏哈希或顺序颠倒 → 返回 false → 测试失败。这是把「本机无法端到端验证」变成运行时事实的关键手法。
3. **反自检**：故意写错期望值，断言 strictMode 确实返回 false（否则「恒真」会让机制静默失效）。

### ★★★ 本阶段最重要的结论：ERC-2771 不能用于全匿名 —— 方案文档 §5.3 的选择是错的

**实测证据**（`test/p5.metatx.test.ts`）：
```
交易 from（原生发送者）:  0x...（中继账户）
签名者（被代表的用户）:   0x...（选民地址）
交易 calldata 长度:       868 字节
签名者地址出现于 calldata: ★ 是
```
**机制**：`ERC2771Forwarder._execute` 执行 `abi.encodePacked(request.data, request.from)`，
而 `request.from` **本身就是 `execute()` calldata 的一部分** → 每笔中继交易必然携带签名者地址。

**根本原因（比机制更重要）**：ERC-2771 的设计目标是让目标合约**识别出**真实用户
（`_msgSender()` 返回签名者），而全匿名要求合约**无法识别**用户 —— **两者目标相反**。
它隐藏的是「谁付 gas」，不是「谁在操作」。

**澄清（避免误判）**：ERC-2771 **本身无安全缺陷**——其重放防护经本项目 6 项测试验证完整。
不采用是「机制与隐私目标冲突」，不是质量问题。该区分必须保留，否则它会被错误拒绝于
**不需要匿名**的场合（免 gas 公开治理投票、空投领取等）。

### 修正后的方案：纯中继（plain relayer）
- 中继账户**直接**提交 `castVote(proof)`，**无链上转发组件**、不用 EIP-712、不用任何签名框架。
- **合约层强制**（新增硬约束 10 / HC-18）：
  `castVote` 首行 `if (IVoterRegistry(REGISTRY).isRegistered(msg.sender)) revert MustUseRelayer();`
  → 阻断「已登记地址直投」这一**唯一必然泄露身份**的路径；
    但**不阻碍匿名路径**：第三方中继账户 ✅、一次性地址自任中继 ✅（后者无法关联身份）。
- **新增硬约束 11 / HC-20**：机械禁止 `Proposal` 引入 `ERC2771Context` / `_msgSender` / `trustedForwarder`。
  ※ 这两条约束若被删，**代码仍能编译、测试仍通过、功能仍可用——只是匿名性静默消失**。
    这是最危险的一类退化，必须机械守护。
- **重放防护改由更强机制承担**：`nullifier` 唯一性（重复提交）+ `scope` 绑定（跨提案/跨链）
  + `message` 绑定（中继篡改即 `InvalidProof`）。F-10 标为「**作废并替代**」而非「已修」。

### ⚠️ 残留风险 R-P5-1（合约层不可覆盖，列为硬约束 12）
**中继在链下知道每个 proof 的来源（IP/会话/时间）**。若记录「proof ↔ 来源」映射，
**中继单独即可完成身份与选票的关联**，ZK 与合约层全部保护失效。
处置：中继不得持久化该映射 + 批量转发打散时序 + 用户可选自任中继。
**边界诚实**：这是运营规范约束，**不是技术强制**——恶意中继可违反它。
R-P5-2：客户端若自行套一层「把身份带入 calldata」的包装，合约看不到 `tx.data` 全貌，无法拦截
（但只伤害操作者自身，前端须禁止）。

### ★★★ 本轮最重要的发现：「覆盖度陷阱」（已固化为硬约束 13）
**首版引擎跑完 512×64 = 32,768 次动作、测试全绿，但实际只覆盖了 1 个提案生命周期。**

统计暴露的现象：
```
finalize(重复) revert 12317 ｜ freezeVotersRoot(重复) revert 15285 ｜ noop ok 5131
registerVoters ok 2 ｜ castVote(诚实) ok 10 ｜ reveal(诚实) ok 3 ｜ finalize ok 1
阶段分布: FINALIZED 32725 / 32768
```
**99.9% 的动作发生在已 FINALIZED 的提案上。** 根因：流程终结后几乎所有动作权重归零，
只剩「必然 revert 的重复调用」与 `noop`，序列在终态无限空转。
**这类缺陷不产生任何失败信号**——每条不变量在终态上本来就恒成立，测试自然全绿。

修正：新增 `spawnLifecycle` 动作（部署新的一组 registry + proposal、重置全部追踪含 `maxPhase`），
并收紧两个「重复」动作的适用窗口（封存后权重归零）。

| 指标 | 修正前 | 修正后 |
| --- | --- | --- |
| 覆盖生命周期 | 1 | **887** |
| castVote(诚实) 成功 | 10 | **3,652** |
| 空转占比 | 99.9% | **10.2%** |
| 耗时 | 8m34s | 8m34s（几乎相同） |

**「跑了 32768 次」与「覆盖了 32768 种状态」的差距可以大到 887 倍。**

⇒ **硬约束 13**：随机/模糊测试必须**统计并断言动作分布与状态覆盖**
（生命周期数、各入口成功率、对抗性动作触发率），且断言值必须非零。
禁止只断言「未发现不变量破坏」。落地形式见 `p6.invariants.test.ts`。

### 路径 A 引擎的四个设计要素（缺一不可）
1. **确定性 PRNG（mulberry32）+ 固定/可覆盖 seed**：绝不用 `Math.random()`
   ——不可复现的随机测试会退化成「偶发失败」，比没有测试更糟（训练团队忽略红灯）。
   测试用地址/数值也不要用 `Wallet.createRandom()`（依赖 Math.random）。
   **所有失败信息必须内嵌 seed + round + step + 动作名 + 复现命令。**
2. **动作分 `legal` / `mustRevert` 两类**：后者是**对抗性动作**（越权、伪造票据、
   重复提交、非法时序），成功执行即判失败——把「合约必须拒绝」变成可断言的事实。
3. **权重而非等权**：等权会让大半调用浪费在必然 revert 的动作上，几万次仍可能没走到
   后半段流程。权重随阶段变化才能穿越完整状态机。
4. **增量检查（必须做）**：每轮线性扫描全部票据并逐张链上查询 ⇒ O(动作数 × 票据数)，
   32768 次下从「1 分钟」恶化到「1 小时」。追踪列表全是 append-only，维护游标只查新增部分，
   复杂度降到 O(动作数 + 票据数)，**检查强度不变**。游标在断言通过后才推进。

### 三个实测踩到的坑
- **`loadFixture` 复用返回值（同一对象引用）**：可变追踪状态放进 fixture 会跨测试污染。
  分工：fixture 只放不可变引用，可变状态每测试新建。
- **`weight()` 是同步的，阶段/时间是异步读的**：需引擎在每次选动作前 `refresh()` 刷新视图快照。
- **时间推进动作在边界耗尽后必须权重归零**：否则会与「唯一能推进流程的动作」抢名额
  （实测 `advanceTime` 曾压制 `finalize`，序列卡在 CLOSED）。

### 一条断言设计原则：读不到的状态不要跳过
合约常刻意让某些查询在特定阶段 revert（如「结果未封存不可读」）。若断言写成
`if (finalized) {...}`，未封存期间它就是个空操作，「每轮无条件调用」失去意义。
改为**断言「此时应有的行为」**——未封存时断言「它必须 revert」，
这样同一条断言在所有状态下都有实质内容，且顺带守护了那条门禁设计。
