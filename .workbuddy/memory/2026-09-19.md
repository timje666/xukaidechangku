## 主题：如何让 Slither/CI 跑在「可达 GitHub 的 CI 环境」

### 关键事实（核实后）
- `.github/workflows/ci.yml` **已存在**完整 CI：含 `slither` 任务（ubuntu-latest + `pip install slither-analyzer==0.10.4` + `--fail-on medium`）。
- `slither.config.json` 的 `"fail_on": "medium"` **正确**：已核对 slither 源码（`FailOnLevel.MEDIUM` → `result["impact"] in ["Medium","High"]`），
  medium 会拦截 High+Medium，满足 DoD「无 High/Medium」，**无需改 fail_on**。
- 阻断交付侧的两点（已修 ci.yml）：
  1. 当前**无 git 远端**（`git remote -v` 空）。
  2. 本地分支 `master`，但 CI 触发写 `[main, develop]` → 推 master 不触发。已改为 `[main, develop, master]`。
- P6 不变量测试（p6/p6b/p6c）经 `npm test`（hardhat test 通配）**已在 CI 执行**；原 ci.yml 注释「【待落地】invariant」已更正为「已落地」。

### 用户疑问：如何"可达 GitHub 的 CI 环境"
- 配置已齐；缺口在**把仓库推到 github.com** 让流水线触发。
- 沙箱 GitHub 不可达（Foundry/solc 下载受阻 + 宿主禁删），故本地 `git push` 不通。
- 可达路径：① 经可联网机器 `git bundle` 搬运后 push；② 自托管 runner（仅出网）；③ 其他托管 CI（GitLab/CircleCI）。
- 关键依赖说明：slither 本体来自 PyPI（不需 GitHub）；但 **solc 二进制**由 py-solc-x 从 `github.com/ethereum/solidity/releases` 下载——这是真正需要 GitHub 可达的环节。
  Docker 镜像 `trailofbits/slither` 自带 solc，可绕开 GitHub 下载（但需 Docker Hub 可达）。

## 主题：评估 github.com/decert-me 是否对本项目有用

### 核实结论
- Decert.me = 开源公共品，用**交互式学习/任务(Quest)给开发者发 SBT**(不可转让链上履历)；栈 Vue/TS + Go + Solidity，部署于 ETH/Polygon 等。
- 核心仓库 `decert-me/contracts`（Hardhat）：`Badge`(SBT) + `Quest` + `QuestMinter`(**后端签名→合约验签→mint**) + `QuestMetadata`；README 只有部署说明，license 未标注。
- **它不是投票系统**，是凭证发行系统；对本项目的核心机制（Semaphore 匿名/时间锁/分步披露/多提案/结果签名验证）**零覆盖**。

### 唯一有价值的接缝：白名单准入(D3) + 强女巫抵抗(D10)
- SBT 不可转让 ⇒ 不可买卖选票；链上可 `balanceOf(addr,id)>0` 无信任校验资格 ⇒ 可把"人工白名单"升级为"持 SBT 才可登记"。
- ★硬约束：**SBT 只能用于登记阶段，绝不能在投票阶段校验**——否则把 地址↔选票 绑定，D2 全匿名直接失效（SBT 本身链上透明，本就不适配隐私场景）。
- 正确流程：登记(身份可见)校验 SBT → 生成 identity commitment 进 Semaphore 组 → 投票只出示 ZK 成员证明。

### 可复用项与成熟度（如实）
- 可参考：`contracts` 的"签名授权铸造 SBT"模式（自建 `VoterCredential`，但 OZ 的 ERC-5192/ERC-4973 更标准）；`zcloak-did`(DID+ZK 凭证方向)。
- 成熟度低：仓库多 0–6 star，`contracts` 最后提交 2024-07；宜"借模式/参考"，**不宜作运行依赖**（引入第三方耦合）。
- 建议：若要强化 D10 论证，做**最小**的"凭证门控登记"演示即可，成本可控。
