## 1. 结论摘要

| 级别 | 数量 | 编号 |
| --- | --- | --- |
| **★ 严重** | 1 | F-02 |
| **高** | 5 | F-01、F-03、F-04、F-05、F-06 |
| **中** | 8 | F-07、F-08、F-09、F-10、F-11、F-13、F-14、F-17 |
| **低** | 7 | F-12、F-15、F-16、F-18、F-19、F-20、F-21 |

**最关键的一条**：F-02 —— 原方案的 `reveal()` 缺少「该承诺确曾在投票期上链」的校验。这一行缺失会使整个防重复投票体系形同虚设：**任何人无需出现在名册中，即可凭空生成任意数量的选票**。这是本次评审中唯一会直接导致业务目标失效的缺陷。

**其余 5 项高危**均属「设计描述与实现语义不一致」类型：接口类型不可编译（F-04）、参数与证明冗余可造假（F-03）、状态写入时点未约束（F-05）、缺关键触发函数（F-06）、状态机枚举语义自相矛盾（F-01）。这类问题在编码阶段才会暴露，但一旦编码完成再修改，代价是合约重写 + 重新审计。

## 2. 详细发现

### 2.1 严重

#### F-02 · `reveal()` 可凭空造票（★ 严重，直接影响业务目标）

| 项 | 内容 |
| --- | --- |
| **原文位置** | v2.0 §5.5 `reveal()` 声明、§6 时序第 ⑰ 步、§7「揭示期校验」行 |
| **问题** | `reveal(payloads)` 的校验链只有三项：① `Poseidon(mask, salt) == ballotCommitment`；② 未揭示过；③ `popcount ≤ maxChoices`。**三项全部可以通过攻击者自造的数据满足** —— 攻击者任意选取 `mask` 与 `salt`，自行计算 `Poseidon(mask, salt)` 得到 `ballotCommitment`，再原样提交即可。 |
| **影响** | 揭示期的票数累计**与投票期完全解耦**。攻击者可在揭示期提交 unlimited 条合法载荷，直接把 `_counts` 刷成任意比例。防重复投票（N1/N2）、名册准入、ZK 匿名凭证全部失效。业务目标（可信投票）直接落空。 |
| **根因** | 设计时把「揭示」理解为「证明我是一个合法票据的持有者」，但实际写成「证明我知道某个哈希的原像」——后者任何人都能构造。缺少的是**票据存在性绑定**。 |
| **修复** | 投票期 `castVote` 中写入 `_commitmentCast[ballotCommitment] = true`；揭示期首行校验 `if (!_commitmentCast[c]) revert CommitmentNotCast();`。已回写 v2.1 §5.4 / §5.5（含完整校验顺序伪代码）/ §5.6 INV-8 / §9.1 R17。 |
| **验证方式** | 新增测试 `test_Reveal_RevertsWhenCommitmentNeverCast()`：构造 `mask/salt` → 计算 `Poseidon` → 直接 `reveal()` → 断言 revert `CommitmentNotCast()`。同时加入不变量 **INV-8**：任一 `ACCEPTED` 的承诺必然满足 `_commitmentCast == true`。 |

### 2.2 高

#### F-01 · `phase()` 状态机语义自相矛盾（新增 IDLE / CLOSED）

| 项 | 内容 |
| --- | --- |
| **原文位置** | v2.0 §5.2 `enum Phase` 实现 |
| **问题** | 两处缺陷：<br/>① 空档期 `registrationEnd ≤ t < votingStart` 返回 `Phase.REGISTRATION`。若 `registerVoters()` 的守卫按常见写法 `require(phase() == Phase.REGISTRATION)` 实现，则**名册锁定后仍可追加登记**，直接破坏 INV-7（名册冻结）。<br/>② `revealEnd` 之后但尚未调用 `finalize()` 时返回 `Phase.FINALIZED`，而 `isFinalized()` 为 `false`，两个对外接口互相矛盾。 |
| **影响** | ① 名册可在投票期被篡改 —— 这是 N1/N2 的核心承诺被推翻；② 前端与索引器会按 `FINALIZED` 渲染结果，而此时结果尚未锁定。 |
| **修复** | 枚举扩展为 `REGISTRATION, IDLE, VOTING, REVEAL, CLOSED, FINALIZED`；`finalized` 布尔决定末态。新增硬约束：**`registerVoters()` 的有效期判断禁止使用 `phase()`**，必须直接比较 `block.timestamp < registrationEnd`。已回写 §5.2。 |
| **验证方式** | `test_RegisterVoters_RevertsInIdleWindow()`：将时间推到空档期 → 调用 `registerVoters` → 断言 revert `RegistrationClosed()`。`test_Phase_ReturnsClosedBeforeFinalize()`。 |

#### F-03 · `castVote` 参数与证明冗余，事件记录可被伪造

| 项 | 内容 |
| --- | --- |
| **原文位置** | v2.0 §5.5 `castVote(uint256 proposalId, bytes32 nullifierHash, bytes32 ballotCommitment, uint256[8] calldata proof, bytes32 merkleRoot, uint256 scope)` |
| **问题** | Semaphore 证明的公开信号本身就包含 `nullifier` 与 `message`。若同时以独立参数传入 `nullifierHash` / `ballotCommitment`，两者之间**没有任何约束**。实现者若直接把这些参数写入事件，则 `BallotCommitted` 事件中记录的 `nullifierHash` / `ballotCommitment` 与真实证明脱节。 |
| **影响** | 链上事件是索引器与审计的唯一数据源。事件失真意味着**审计结论失真**：复算出的结果与链上真实票数不一致，N6 的「结果可核验」失效。 |
| **修复** | `castVote` 改为只接收 `ZKProof` 结构体，`nullifier` 与 `ballotCommitment = uint256(proof.message)` 一律从证明中读取。已回写 §5.4 / §5.5。 |
| **验证方式** | ABI 层面即可发现（单参数）；测试 `test_CastVote_EventMatchesProofSignals()` 断言事件字段与证明公开信号逐一相等。 |

#### F-04 · `uint256[8] calldata proof` 类型不成立

| 项 | 内容 |
| --- | --- |
| **原文位置** | v2.0 §5.5 |
| **问题** | Semaphore v4 的 Groth16 验证器需要一个包含 **4 个公开信号**（`merkleTreeRoot`、`nullifier`、`message`、`scope`）与 **8 个证明点**的复合结构。仅传 `uint256[8]` 无法表达公开信号，**与官方 `SemaphoreVerifier` 接口不兼容，无法编译对接**。 |
| **影响** | P4 阶段（Semaphore 集成）必然返工；若实现者自行拼凑参数顺序，会引入静默的验证错误。 |
| **修复** | 新增 `struct ZKProof { merkleTreeRoot; nullifier; message; scope; points[8]; }`，接口改为 `castVote(ZKProof calldata proof)`。已回写 §5.4 / §5.5。 |
| **验证方式** | `forge build` 通过且与 `semaphore-protocol/contracts` 的 `ISemaphoreVerifier` 可直接对接（P4 的 DoD）。 |

#### F-05 · `_nullifierUsed` 的写入时点未受约束

| 项 | 内容 |
| --- | --- |
| **原文位置** | v2.0 §9.2 优化点 G8 |
| **问题** | G8 仅规定「ZK 验证放最后」以省 gas，**未规定状态写入的时点**。若实现者按「先标记 `nullifier` 已用，再验证证明」的自然顺序书写，则未经验证的任意 `nullifier` 值都会被写入状态。 |
| **影响** | 攻击者可用随机 `nullifier` 批量写入 `_nullifierUsed`（每条约 20k gas），造成状态无限膨胀；更严重的是，若攻击者写入的 `nullifier` 恰好与某合法选民的相同，该选民将**永久无法投票**（DoS）。 |
| **修复** | G8 修正为明确顺序：`时间窗 → frozenRoot → scope → nullifier 未用（只读） → verifyProof → 写入`。并新增不变量 **INV-9**：`_nullifierUsed[n] = true` 必然发生在 `verifyProof` 成功之后。已回写 §9.2 / §5.6 / §5.5 注释。 |
| **验证方式** | 不变量测试 + 代码评审检查点（P4 DoD）。 |

#### F-06 · 缺少 `frozenRoot` 的固化触发机制

| 项 | 内容 |
| --- | --- |
| **原文位置** | v2.0 §5.4 `ProposalState.votersRoot` 注释、§6 时序第 ⑦ 步「registrationEnd 后冻结根」 |
| **问题** | 全文要求「投票期校验 `proof.merkleTreeRoot == frozenRoot`」，但**从未定义 `frozenRoot` 由谁、在何时、通过哪个函数写入**。第 ⑦ 步的「冻结」是一个没有载体的动作。 |
| **影响** | 若根在投票期继续增长（登记与投票时间窗若被允许重叠），**先投票选民的证明会全部失效**。或实现者直接把 `votersRoot` 当 `frozenRoot` 用，则 INV-7 无法成立。 |
| **修复** | 新增无权限门槛的函数 `freezeVotersRoot()`：`registrationEnd` 之后任何人可调用一次，幂等，固化根并发 `VotersRootFrozen` 事件；`castVote` 校验 `frozenRoot != 0 && proof.merkleTreeRoot == frozenRoot`。已回写 §5.4 / §5.5。 |
| **验证方式** | `test_FreezeVotersRoot_IsIdempotent()`、`test_CastVote_RevertsWhenRootNotFrozen()`、`test_CastVote_RevertsAfterRootChange()`。 |

### 2.3 中

#### F-07 · INV-1 缺少运行计数器，无法被断言

- **问题**：`sum(counts) == sum(popcount(revealedMasks))` 需要全量 `revealedMasks`，合约并未存储。
- **影响**：INV-1 是一句无法执行的断言，不变量测试（P6）无法落地。
- **修复**：新增 `uint64 totalMarks`，每次成功揭示累加 `popcount`；INV-1 改为 `sum(counts) == totalMarks`。已回写 §5.4 / §5.6。

#### F-08 · 揭示失败的票无法标记，可被无限重试

- **问题**：因 `popcount > maxChoices` 被拒的承诺，`_commitmentRevealed` 未置位 → 可被反复提交，每次空耗 30k+ gas。
- **影响**：gas 被恶意空耗；`RevealRejected` 事件被刷屏，索引器数据膨胀。
- **修复**：改为 `mapping(bytes32 => RevealStatus)`（`NONE / ACCEPTED / REJECTED`），拒绝后置 `REJECTED`，再次提交直接 revert。已回写 §5.4 / §5.5 伪代码。

#### F-09 · `registerVoters` 批量上限与 gas 估算均错误

- **问题**：原文写「每地址 20,000–25,000 gas、每批 ≤ 200 地址」。实际每地址需「`whitelist[addr]` 一次 SSTORE（20k）+ LeanIMT 插入（40–80k）」≈ **60–100k**。200 地址约 **12–20M gas**，逼近单笔交易 gas 上限，L2 排序器亦可能拒收。
- **影响**：P2 阶段登记交易大概率失败；采购与成本核算低估 3–4 倍。
- **修复**：单批上限改为 **50**，gas 修正为 60–100k/地址，并给出「分批多次登记」的脚本策略。已回写 §9.2。

#### F-10 · Forwarder 的 EIP-712 签名覆盖范围未定义

- **问题**：`ForwardRequest` 列出了字段，但未规定签名必须覆盖哪些。若未绑定 `data` 的哈希，**同一签名可被重放至任意 calldata**；若未校验 `deadline`，签名永久有效；若未绑定 `to`，签名可跨提案重放。
- **影响**：高危重放风险，中继资产可被盗用。
- **修复**：新增硬约束 4 —— 类型哈希必须覆盖 `from/to/value/gas/nonce/deadline/keccak256(data)`，并校验 `deadline` 与 `nonce`。已回写 §5.3 / §9.1 R18。

#### F-11 · 匿名性的边界未声明，存在对外误述风险

- **问题**：全文使用「全匿名」，但链上 `BallotCommitted` 事件同时记录 `nullifier` 与 `ballotCommitment`，揭示后可建立 `nullifier ↔ 选项` 的公开关联。真实性质是**不可链接到真实身份（假名性）**，而非不可链接。
- **影响**：公示文案若声称「完全匿名/不可追溯」，属于**失实陈述**，可能引发合规与信任争议。
- **修复**：新增 §4.2「匿名性边界」表，明确「能成立 / 不能成立」两栏，并规定对外表述口径。已回写 §4.2。

#### F-13 · Q8 的补贴形式与 §4.2 信任模型矛盾

- **问题**：Q8 推荐「按揭示次数提供 gas 补贴」。若补贴以「Relayer 代发 reveal 交易」实现，则 Relayer 的 calldata 中含揭示明文，Relayer 即获知该票内容 —— 与 §4.2「Relayer 看不到选项明文」直接冲突。
- **修复**：与 Q12 对齐 —— 揭示交易由**选民自行广播**；补贴改为**事后按链上 `BallotRevealed` 记录向选民地址报销**。已回写 §0.3 Q8 / §5.3 服务范围 / §11。

#### F-14 · `CLOSED` 窗口的对外口径未定义

- **问题**：`revealEnd` 之后、`finalize()` 之前，`getCounts()` 仍 revert，但 `_counts` 的原始 storage 在公开链上客观可读。
- **影响**：若 UI 在该窗口显示「计票中」而数据实际可读，会出现「结果已泄但官方未公布」的口径错位。
- **修复**：新增硬约束 3：该窗口内 UI 与接口层必须统一显示「计票中」，**不得把揭示尾期数据当作最终结果**。已回写 §5.2。

#### F-17 · 揭示率未达标的兜底设计缺失

- **问题**：P12 的 DoD 要求「揭示率 ≥ 95%」，但全文未定义未达标时的处置。直觉方案「延长揭示窗口」与 N3（不可延时）直接冲突。
- **影响**：验收标准成为无法执行的指标；实施团队会在 P12 卡住。
- **修复**：明确 **揭示窗口不可延长**，未揭示票永久作废；揭示率降级为**监控指标而非可回退项**，只能靠前端强引导。已回写 §12 AS-17。

## 4. 未变更的结论

以下 v2.0 的核心判断经本次评审**确认成立**，无需修改：

1. **C1 两段式准入 + Relayer 是全匿名的必要条件** —— 逻辑闭环，无漏洞。
2. **C2 承诺—揭示双层** —— 投票期票数密码学不可读；「揭示期渐进公开无跟风风险」的论证成立（投票已结束，不存在后续投票者）。
3. **C3 结果哈希锚定取代「合约签名」** —— 表述正确，EVM 合约确无私钥。
4. **C4 移除全部暂停能力** —— 与 N3 一致，无残留接口。
5. **不变量设计方向** —— INV-1 ~ INV-9 的语义均正确，仅 INV-1 缺计数器（已补）。
6. **多提案「一实例一合约」** —— 隔离性与成本权衡合理。
7. **不引入代币质押（S10）** —— 与合规硬约束的冲突判断正确。

## 5. 评审结论

**v2.0 的架构判断全部成立，v2.1 修复了 21 项实现层缺陷后可进入 P0。**

需要特别说明：F-02 的存在说明**「设计文档通过评审」不等于「实现安全」**。建议在 P4（Semaphore 集成）与 P6（不变量测试）之间增加一次**专项安全走查**，重点复核三类路径：

1. **状态变更路径**：每个 `mapping` 写入是否都有前置的存在性/合法性校验；
2. **外部输入路径**：凡是来自 calldata 的值，是否都经过链上验证而非直接采信；
3. **批量接口路径**：批量循环中的单条失败是否会影响整批，是否存在可被反复触发的失败分支。

这三类正好覆盖了 F-02、F-03、F-05、F-08 的共同根因。
