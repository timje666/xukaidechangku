@semaphore-protocol/contracts@4.14.3
  └── @zk-kit/lean-imt.sol@2.0.1
        └── poseidon-solidity@0.0.5

| 判据 | 结果 |

## 3. 问题 2：编译兼容性

| 依赖文件 | pragma | 与 `0.8.24` 兼容 |
| --- | --- | --- |
| `@zk-kit/lean-imt.sol/LeanIMT.sol` | `^0.8.4` | ✅ |
| `@zk-kit/lean-imt.sol/InternalLeanIMT.sol` | `^0.8.4` | ✅ |
| `@semaphore-protocol/contracts/base/SemaphoreVerifier.sol` | `>=0.8.23 <0.9.0` | ✅ |

编译结果：`Compiled 5 Solidity files successfully (evm target: paris)`。

### 3.1 API 形状（已确认，供 P2/P3 直接使用）

```solidity
// InternalLeanIMT（internal，编译期内联）
struct LeanIMTData {
    uint256 size;
    uint256 depth;
    mapping(uint256 => uint256) sideNodes;
    mapping(uint256 => uint256) leaves;
}
function _insert(LeanIMTData storage, uint256) internal returns (uint256);
function _insertMany(LeanIMTData storage, uint256[] calldata) internal returns (uint256);
function _update(...) internal;
function _remove(...) internal;
function _has(LeanIMTData storage, uint256) internal view returns (bool);
function _indexOf(LeanIMTData storage, uint256) internal view returns (uint256);
function _root(LeanIMTData storage) internal view returns (uint256);
```

### 3.2 ★ 关键发现：本版本**不提供** `generateProof` / `verifyProof`

`LeanIMT` 与 `InternalLeanIMT` 均只有 `insert / insertMany / update / remove / has / indexOf / root`。

**影响（对 P3 是决定性简化）**：

| 环节 | 在哪里做 | 说明 |
| --- | --- | --- |
| 成员证明生成 | **链下**（zk-kit 的 lean-imt JS 包） | 前端从名册快照重建树，生成 Merkle 路径 |
| 成员证明校验 | **ZK 电路** | Semaphore 电路在证明内部校验 Merkle 路径 |
| 合约职责 | 仅比对 `proof.merkleTreeRoot == frozenRoot` | **无需在链上重算 Merkle 路径**，也无需存储路径 |

⇒ VoterRegistry 只需维护树的**根**，不需要任何 `verifyProof` 接口。

## 4. 问题 3：库链接依赖（**原假设被推翻**）

### 4.1 原假设

> 「使用 `InternalLeanIMT`（internal 函数，编译期内联）而非 `LeanIMT`（public 函数），
> 即可让 VoterRegistry **单合约独立部署**，不引入库链接。」

### 4.2 实测结果：**假设不成立**

```
库链接依赖检查
  ⚠️ 需要外部库链接: 1 个
       ℹ️ 已登记  DependencyProbe
           → PoseidonT3 (poseidon-solidity/PoseidonT3.sol)
```

**根因**：`InternalLeanIMT._insert` 内部调用 `PoseidonT3.hash(...)`，而 poseidon-solidity 的
`PoseidonT3.hash` 签名是 **`public`**：

```solidity
library PoseidonT3 {
    function hash(uint[2] memory) public pure returns (uint);  // ← public，非 internal
}
```

`public` 库函数**不会被内联**，必然产生链接引用。选用 `InternalLeanIMT` 只能**少一层**链接（LeanIMT 自身），**无法消除** Poseidon 层的链接。

### 4.3 处置

| 项 | 内容 |
| --- | --- |
| 是否可回避 | **否**。任何在链上维护 Semaphore 兼容 Merkle 树的合约都必须调用 `PoseidonT3.hash`。除非改为链下建树（见 §6 的否决理由） |
| P8 部署脚本要求 | **① 先部署 `PoseidonT3` 库合约并记录地址 → ② 部署业务合约时传 `{ libraries: { PoseidonT3: <addr> } }` → ③ 区块浏览器验证时一并提供库地址** |
| 工具化 | 新增 `scripts/check-link-references.mjs`，把该依赖登记为**预期链接**；任何**未登记**的链接引用会导致门禁失败（拦住「本可内联却误用 public 版库」的写法） |
| 代码修正 | `DependencyProbe.sol` 的 `@dev` 中原本写着「可保持单合约部署」，**该错误结论已更正** |

## 5. 问题 4：★ 成本实测（决定架构）

### 5.1 测量方法

链上建树是否可行，取决于「每片叶子的插入成本」。而 `LeanIMT` 的成本直觉上是 `O(depth)`，
若按此假设外推，10 万选民（depth≈17）会比 200 叶样本（depth≈8）贵一倍以上。
**因此不能只测小样本做线性外推**，必须在不同规模段分别测量趋势。

### 5.2 实测数据

| 规模 | 实测树深 | 每叶均摊 gas |
| --- | --- | --- |
| 64 叶 | 6 | 59,198 |
| 512 叶 | 9 | 57,871 |
| 2,048 叶 | 11 | 58,496 |
| — | — | **随树深变化：0.99x（平坦）** |

单次调用参照：

| 操作 | gas |
| --- | --- |
| 第 1 片叶子 `insert` | 93,330 |
| 第 2 片叶子 `insert` | 132,488 |
| `insertMany(50)` 合计 | 3,006,131（均摊 60,122 / 叶） |

### 5.3 ★ 结论：成本**不随树深增长**

每叶成本在 depth 6→11 区间**基本恒定（比值 0.99）**。

**原因**：LeanIMT 的 `_insert` 只在 `sideNodes[level]` 为空时才向上哈希，连续插入下哈希次数呈
**二进制进位模式**——约一半的插入只需 0~1 次哈希。**均摊为 O(1)，而非 O(depth)。**

> **方法学警示**：若按「小样本均摊 × 规模」或「按 O(depth) 线性放大」外推，都会得出错误结论。
> 本次实测直接推翻了 O(depth) 假设。**凡涉及随规模变化的成本外推，必须做分段趋势测量。**

### 5.4 10 万选民规模推算

| 指标 | 数值 |
| --- | --- |
| 每叶 gas | 约 58,500 |
| 建树总 gas | 约 **59 亿** |
| L2 量级成本（0.02 gwei / ETH 3,000 USD） | 约 **350 USD**（**量级估算，非承诺**） |
| 批次数（每批 64） | 约 **1,563 笔交易** |

### 5.5 可行性判据

```
实测每叶 59,199 gas；2 倍安全余量 = 118,397 gas（阈 200,000）→ ✅ 通过
```

**保留「合约维护 Merkle 树」的强安全模型**：名册根由合约从登记数据推导，
而非由管理员提交一个无法链上校验的数值。

## 6. 被否决的备选方案

| 方案 | 说明 | 为何否决 |
| --- | --- | --- |
| **链下建树 + 仅上链根** | 管理员在链下算根，合约只存根 | gas 可再降约 10 倍、且**彻底消除 Poseidon 链接依赖**；但名册根从「合约推导」退化为「管理员提交」，一致性只能事后由第三方重放事件校验。**在成本可接受（约 350 USD）的前提下，没有理由放弃可链上校验的强模型** |
| 使用 `LeanIMT`（public 版） | — | 多一层库链接，无任何收益 |
| 改用 Keccak Merkle（OZ `MerkleProof`） | 无链接、gas 低 | **与 Semaphore 电路不兼容**（电路要求 Poseidon 树），P4 无法集成 |

## 7. 对 P2 / P3 / P8 的直接影响

| 阶段 | 影响 |
| --- | --- |
| **P2** | `VoterRegistry` 采用 `InternalLeanIMT` + `LeanIMTData`，在链上维护树；**单批 ≤ 50 地址**（≈ 4M gas 含白名单 SSTORE）；必须发**带序号的插入事件**供链下按序重建 |
| **P3** | `castVote` **不需要** Merkle 路径校验——只比对 `proof.merkleTreeRoot == frozenRoot`，路径正确性由 ZK 电路保证 |
| **P4** | `ISemaphoreVerifier` 接口可被引用（已验证），无 API 阻碍 |
| **P8** | 部署顺序变为三步：`PoseidonT3` → `VoterRegistry`(链接) → `ProposalFactory`；验证源码需提供库地址 |
