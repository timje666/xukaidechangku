# P5 交付记录 —— 匿名准入与中继模型（含架构级修正 F-23）

> 阶段：P5（原定「`MinimalForwarder` 中继 / ERC-2771」）
> 日期：2026-09-18
> 结论：**原定的 ERC-2771 方案经实测证伪，已改为纯中继模型**。这是本项目迄今
> 唯一一次**架构级**修正（此前 F-01 ~ F-21 均为设计层，F-22 为环境层）。

---

## 1. 核心结论（必读）

**ERC-2771 不能用于全匿名投票。** 它会把签名者地址明文写入交易 calldata。

### 1.1 实测证据

一笔经 `ERC2771Forwarder` 转发的调用，其链上交易：

```
┌─ ERC-2771 身份泄露实测 ───────────────────────────
│ 交易 from（原生发送者）:  0x...（中继账户）
│ 签名者（被代表的用户）:   0x...（选民地址）
│ 交易 calldata 长度:       868 字节
│ 签名者地址出现于 calldata: ★ 是
└──────────────────────────────────────────────────
```

对照：纯中继（中继账户直接提交 `castVote(proof)`）交易中，
中继地址、已登记选民地址均**不出现**于 calldata。

### 1.2 机制原因

`ERC2771Forwarder._execute` 执行：

```solidity
bytes memory data = abi.encodePacked(request.data, request.from);
```

而 `request.from` **本身就是 `execute()` calldata 的一部分**。故每笔中继交易
必然携带签名者地址。

### 1.3 根本原因（比机制更重要）

| | ERC-2771 的设计目标 | 本项目的目标 |
| --- | --- | --- |
| 目标 | 让目标合约**识别出**真实用户（`_msgSender()` 返回签名者） | 让目标合约**无法识别**真实用户 |
| 隐藏什么 | 「谁付 gas」 | 「谁在操作」 |

**两者目标相反。** 因此原判断「Relayer 是全匿名的必要条件」方向正确，
但「用 ERC-2771 实现」在机制上必然失败——它**以机制保证**地址上链。

### 1.4 澄清：ERC-2771 本身无安全缺陷

其重放防护经本项目测试验证**完整**（同签名换 calldata / 换目标 / 过期 / nonce 复用 /
签名者不符 / 未信任目标，6 项全部被正确拒绝）。

不采用它是**机制与隐私目标冲突**，而非质量问题。
该区分必须保留——否则它会被错误地拒绝于**不需要匿名**的场合
（免 gas 的公开治理投票、空投领取、NFT 白名单领取等）。

## 2. 已实施的修正

### 2.1 合约层：`castVote` 增加匿名准入强制

```solidity
function castVote(ISemaphore.SemaphoreProof calldata proof) external {
    // ⓪ 【★全匿名强制点】禁止已登记地址直接提交
    if (IVoterRegistry(REGISTRY).isRegistered(msg.sender)) revert MustUseRelayer();
    ...
}
```

**为什么这是有效的**——它阻断唯一必然泄露身份的路径，且不阻碍匿名路径：

| 提交方式 | 结果 | 是否匿名 |
| --- | --- | --- |
| 第三方中继账户提交 | ✅ 通过 | 匿名（中继与身份无关） |
| 一次性地址自任中继 | ✅ 通过 | 匿名（一次性地址无法关联身份） |
| **名册中已登记的地址提交** | ❌ **拒绝** | —— 这正是会导致 `地址 ↔ 选票` 关联的路径 |

**代价**：一次跨合约静态调用（冷 SLOAD 约 2.1k gas）。
`castVote` 实测均值 115,169 gas（P4 为 110k–119k），增量约 2–3k，可接受。

**无单点依赖**：任何账户均可自任中继；平台中继仅提供「免 gas」便利，其不可用
不影响功能可用性（已由测试验证）。

### 2.2 移除 ERC-2771 相关代码

- 删除 `contracts/forwarder/ChainVoteForwarder.sol`
- `ProposalInit` 移除 `forwarder` 字段
- 移除 `trustedForwarder()` / `isTrustedForwarder()` / `_trustedForwarder`
- 移除 `Errors.sol` 中为自研中继预设的 4 个错误（`DeadlineExpired` /
  `InvalidSignature` / `NonceUsed` / `ForwardFailed`）

### 2.3 保留证据（关键）

| 文件 | 作用 |
| --- | --- |
| `contracts/harness/ERC2771LeakReference.sol` | 参照中继 + 最小目标探针。**不参与生产部署**，唯一用途是让泄露可复现 |
| `test/p5.metatx.test.ts` 的「身份泄露判定」用例 | 可执行的证据。任何人可在 1 秒内重新验证该判断 |

**为什么保留而非删除**：若只写结论，后续维护者可能「为了标准化」而重新引入 ERC-2771。
可执行证据的成本极低，而防止架构回退的价值很高。

## 3. 纯中继下的重放防护（F-10 的等价物）

纯中继没有 EIP-712 签名，原 F-10 的「nonce / deadline / data 绑定」**不再适用**。
替代保护**更强**，因为它绑定在投票语义上而非传输层上：

| 攻击 | 防护 | 依据 |
| --- | --- | --- |
| 同一 proof 重复提交 | `AlreadyVoted()` | `nullifier` 由 ZK 电路派生，每人每提案唯一 |
| 同一 proof 投向另一提案 | `InvalidScope()` | `SCOPE = H(domain, chainId, proposal)` 全局唯一 |
| 跨链重放 | `InvalidScope()` | `chainId` 已入 `SCOPE` |
| 中继篡改 proof 内容 | `InvalidProof()` | proof 由选民生成并绑定 `message`（选票承诺） |

**F-10 在方案 §15 中已标注「作废并替代」**，而非「已修」——避免留下
「EIP-712 校验已实现」的错误印象。

## 4. ⚠️ 残留风险（必须记录）

### R-P5-1 中继的链下元数据泄露（合约层不可覆盖）

中继收到请求时能看到 **IP、会话、时间**。若它记录「proof ↔ 请求来源」映射，
则**中继单独即可完成身份与选票的关联**——ZK 与合约层的所有保护均失效。

**处置**（列为硬约束 12）：
- 中继服务**不得持久化** proof 与来源的对应关系；写日志前剥离来源字段
- 采用**批量转发**（积攒若干请求后按随机顺序提交）打散时序关联
- 用户侧可选自任中继（一次性地址）完全规避

**边界诚实说明**：这是运营规范约束，**不是技术强制**。一个恶意中继可以违反它。
但违反的后果是「中继自曝其可信度」——它不改变链上数据的性质，只影响该中继的
用户是否被关联。

### R-P5-2 客户端包装机制（合约不可见）

若客户端使用某种「把身份带入 calldata」的包装机制（如自行套一层 ERC-2771），
合约看不到 `tx.data` 全貌，无法拦截。

**评估**：该行为只会伤害操作者自身（主动暴露），不构成对他人的攻击面。
前端实现必须禁止此类包装（已列入 P9/P10 前端要求）。

## 5. 新增硬约束与机械守护

| 编号 | 内容 | 守护 |
| --- | --- | --- |
| **硬约束 10** | `castVote` 必须含 `!isRegistered(msg.sender)` 检查 | **HC-18**（含自检用例） |
| **硬约束 11** | `Proposal` 不得引入 `ERC2771Context` / `_msgSender` / `trustedForwarder` | **HC-20** |
| **硬约束 12** | 中继不得持久化「proof ↔ 来源」映射 | 运维规范（无法机械守护，须审计） |

**HC-18 与 HC-20 的必要性**：这两条约束若被删除，**代码仍能编译、测试仍会通过、
功能仍然可用**——只是匿名性静默消失。这是最危险的一类退化，
必须由机械守护而非人工评审来防止。

## 6. 工程改动（顺带的根治性修复）

### 6.1 共享夹具构造器（根治「加字段破坏下游」）

`ProposalInit` 已两次因新增必填字段而中断下游测试（P4 加 `verifier`、P5 加 `forwarder`），
根因是各测试**各自内联构造** init，字段定义分散在 N 处。

处置：新增 `test/helpers/proposal.ts`，统一 `buildProposalInit()` 与 `buildTimeWindows()`。
**新增字段时只改一处。**

效果立竿见影：本阶段回退 `forwarder` 字段时，只改了 1 个文件 + 2 处 fixture 调用，
而非逐个测试文件排查。

同时把「时窗留余量」的规则也收敛进去——该规则此前只在注释里，
而 Hardhat「每块时间戳严格递增」叠加合约的 `>=` 边界判断，
导致 fixture 必须留 ≥2 秒余量（P3 曾因此 34 项测试全挂）。

### 6.2 清理死错误（Errors.sol）

发现 10 个零引用的错误声明，已删除：

```
NotInPhase / RegistrationNotOpen / InvalidMaxChoices / ProposalNotRegistered   ← 从未使用
ChoiceLimitExceeded / MaskOutOfRange    ← P3 改用 REASONS 码 + 事件，不再抛错
DeadlineExpired / InvalidSignature / NonceUsed / ForwardFailed   ← 为自研中继预设，方案已作废
```

**为什么值得单独做**：死错误会让审计者认为存在某条失败路径，而实际没有——
与死代码同样有害。新增 **HC-19** 机械守护「Errors.sol 中每个声明必须至少被引用一次」。

### 6.3 测试文件重命名

`p5.forwarder.test.ts` → `p5.metatx.test.ts`（因为内容已从「中继功能测试」
变为「中继模型判定 + 匿名准入」）。

## 8. P5 完成标准核对

| 原定完成标准 | 状态 | 说明 |
| --- | --- | --- |
| EIP-712 类型哈希覆盖 `keccak256(data)` 与 `to` | ⚠️ **不适用的前提** | 方案已作废；改由 `nullifier` 唯一性与 `scope` 绑定承担重放防护（更强） |
| 校验 `deadline` / `nonce` | ⚠️ **不适用的前提** | 同上 |
| 同签名换 calldata 重放必拒 | ✅ 已验证 | 作为**参照组**保留（证明 ERC-2771 本身无缺陷） |
| 跨提案重放必拒 | ✅ 已验证 | 在纯中继模型下重新验证 |
| 过期签名必拒 | ✅ 已验证 | 参照组 |
| nonce 复用必拒 | ✅ 已验证 | 参照组 |
| `sender` 与选民解耦（链上无法关联） | ✅ **已强化验证** | 不止「解耦」，而是断言**交易 calldata 与事件中均不含选民地址** |

> **完成标准被重新定义的原因**：原标准全部围绕 ERC-2771 的签名机制，
> 而该机制本身已被否决。新标准更严格——它直接断言「地址不上链」，
> 而非只断言「签名框架正确」。

## 10. 一句话总结

**原方案的信任模型是对的，但实现机制与目标相反。** 修正后：
匿名性不再依赖「中继是否守规矩」——合约层直接禁止了唯一会泄露身份的提交方式；
中继即使完全恶意，也无法从链上数据把票关联到人。
唯一残留风险在中继的**链下日志**，已列为硬约束 12 并交由运维审计。
