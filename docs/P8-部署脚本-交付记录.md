## 1. 交付目标

按方案 v2 §10，把「可复现、可审计、可验证」的部署能力补齐：

1. **部署脚本**：以**固定顺序、同一账户、CREATE** 部署全部合约，产物落 `deployments/<network>.json`。
2. **Timelock（治理时间锁）**：承载工厂的 `DEFAULT_ADMIN_ROLE` 与 `CREATOR_ROLE` 授予，使任何权限变更都经过「排程 → 等待 → 执行」延时窗口。
3. **多签**：生产链排程权强制落到多签（如 Safe），部署者 EOA 不得长期持有治理权限。

三条 DoD：

- **① anvil 二次执行地址一致** —— 地址只由 `(deployer, nonce, 固定参数)` 决定，无随机量。
- **② 部署者无业务角色** —— 部署者既不留 `DEFAULT_ADMIN`、也不持 `CREATOR_ROLE`。
- **③ 浏览器可验证** —— 产物含构造参数、库地址、salt、operationId，源码验证的全部输入齐备。

## 3. 关键设计决策

### 3.1 Timelock 包装（治理时间锁）

`Timelock` 直接继承 `OpenZeppelin TimelockController v5.0.2`，仅叠加一条常量与一道 fail-closed 校验：

```solidity
contract Timelock is TimelockController {
    uint256 public constant MIN_TIMELOCK_DELAY = 2 days;
    constructor(uint256 minDelay, address[] memory proposers,
                address[] memory executors, address admin)
        TimelockController(minDelay, proposers, executors, admin) {
        if (minDelay < MIN_TIMELOCK_DELAY) revert TimelockDelayTooShort(minDelay, MIN_TIMELOCK_DELAY);
    }
}
```

- **下限 fail-closed**：构造期拒绝低于 2 天的延时，任何「借 `--min-delay 60` 绕过」的部署直接 revert。
- **自管理**：`admin = 零地址` 时 `DEFAULT_ADMIN_ROLE` 由合约自身持有，无 EOA 持有无延时管理员（测试已断言）。
- **执行者开放**：`executors = [零地址]`，表示任何人均可在窗口到期后执行，避免单点卡死。
- **只承载治理角色**：Timelock 不继承 `ChainVoteAccessControl`——其角色集（`PROPOSER/EXECUTOR/ADMIN`）与业务角色（`CREATOR_ROLE` 等）不同源；若强行继承会让 `roleMatrix` 说谎。它仅持有工厂的 `DEFAULT_ADMIN_ROLE`，并负责排程 `CREATOR_ROLE` 授予。
- 编译后 **6746 B（27.4% EIP-170）**，远低于上限。

### 3.2 部署顺序与库链接（P7 移交的硬约束）

顺序不可调整（与 `check-link-references.mjs` 一致）：

```
PoseidonT3 → PoseidonT4 → SemaphoreVerifier → Timelock → ProposalFactory
```

- `PoseidonT3` 链接进 `VoterRegistry`、`PoseidonT4` 链接进 `ProposalFactory`（部署时 `{ libraries: { PoseidonT4 } }`）。
- `SemaphoreVerifier` 无构造参数、无需链接；**必须是官方实现，不得为 `MockVerifier`**（P4 交付记录 §3.3 的 P8 必做项，测试逐字节比对运行时字节码）。
- `ProposalFactory` 构造传入 `[timelock.address]` 作为初始管理员（即 `PROPOSAL_ADMIN` immutable 冻结为 Timelock）。
- 部署前用 `ethers.getCreateAddress` 预测 `nonce0+i` 地址并比对自检；部署后 `assertLibrariesLinked` 直接读**运行时字节码**的 `deployedLinkReferences` 槽（非 `linkReferences` 创建码偏移），确保库确实填入每个链接槽。

### 3.3 地址确定性（DoD ①）

全部合约由**同一账户（`signers[0]`）、固定顺序、固定参数**以 CREATE 部署，不使用 CREATE2、不引入随机 salt。因此地址是 `(deployer, nonce)` 的纯函数：

```
address_i = getCreateAddress({ from: deployer, nonce: deployNonce0 + i })
```

`deployAll` 在部署前读取 `deployerNonce(deployer)` 记为 `deployNonce0` 并写回产物，使「地址只由 nonce 决定」这一性质可被测试精确验收，而无需假设「从 nonce 0 开始」（见 §6 本轮回填）。

### 3.4 部署者无业务角色（DoD ②）

- 工厂 `DEFAULT_ADMIN_ROLE` 与 `PROPOSAL_ADMIN` 均为 Timelock；部署者仅作为「部署交易的发起人」，部署后即不再持有任何角色。
- `CREATOR_ROLE` 经时间锁排程授予 `electionAdmin`；本地链默认 `electionAdmin = signers[1]`。
- 测试断言：部署者 `hasRole(DEFAULT_ADMIN)` = false、`hasRole(CREATOR_ROLE)` = false。

### 3.5 角色排程与快进

- **本地链（默认）**：`FAST_FORWARD=true`，排程后 `time.increase(minDelay+1)` 立即执行，使本地环境处于「已配置」状态，便于闭环与冒烟。
- **生产链**：强制 `TIMELOCK_PROPOSER`（应为多签地址），缺失即 fail-closed 拒绝部署；排程后由 `execute-operation.ts` 在延时期满后执行（本地已快进环境检测 `isOperationReady` 后跳过）。
- 排程 `salt` 为固定常量 `ethers.id("chainvote:grant:CREATOR_ROLE")`，保证同一份配置产生同一 `operationId`，可事前复算（审计友好）。`operationId` 含目标地址，随工厂地址变化属正确行为；断言的是「可由记录字段链上复算」，而非「两轮相同」。

### 3.6 浏览器可验证（DoD ③）

产物 `deployments/<network>.json` 每个合约记录：

- `address` / `txHash` / `blockNumber` / `gasUsed`
- `constructorArgs`（源码验证所需的全部构造参数）
- `libraries`（含库链接的工厂写明 `PoseidonT4` 地址）
- `timelockOperations[]`：`operationId` / `target` / `signature` / `args` / `data` / `salt` / `state`

`verify-deployment.ts` 直接复用这些字段做 `hardhat verify:verify`（跳过本地链；`Already Verified` 视为通过）。

### 3.7 确定性门禁（CI 门禁 6）

`scripts/check-deploy-determinism.mjs` 在**两个相互独立的进程**里各跑一次 `hardhat run script/deploy.ts --network hardhat`，各自落在全新内存链上，逐字段比对产物：

- 忽略两处**按定义不可复现**的字段：`deployedAt`（墙钟时间）、`timelockOperations[].eta`（链上时间戳 = 排程区块 + 延时）。
- 其余字段（地址、txHash、blockNumber、构造参数、salt、operationId）必须逐位一致；**txHash 一致**是强旁证（要求 nonce/calldata/gas 定价全一致）。
- 实测两次部署的 5 个合约地址完全一致（标准 Hardhat 确定性序列：`5FbD…80aa3` / `e7f1…F0512` / `9fE4…fa6e0` / `Cf7E…0Fc9` / `Dc64…fC6C9`）。
- 该门禁接入 `npm run verify` 与 `ci.yml`，对应 DoD ① 的「换台机器 / 重置链」语义。

### 3.8 Foundry `forge script` 的 Hardhat 等价替代

原方案 v2 写的是 Foundry `forge script`。因 GitHub 不可达、Foundry 无法安装（P0 决策），本里程碑以 **Hardhat 等价实现**落地，差异如下：

| 维度 | 原方案（Foundry） | 本实现（Hardhat） |
| --- | --- | --- |
| 部署入口 | `forge script Deploy` | `hardhat run script/deploy.ts` |
| 确定性地址 | CREATE2 / 固定 salt | CREATE + 固定 nonce 顺序（无 salt） |
| 跨进程复现门禁 | anvil 二次执行 | 两个独立 `hardhat` 进程 + 产物逐字段比对 |
| 验证 | `forge verify-contract` | `hardhat verify:verify` |

确定性目标等价达成（地址只由部署参数决定）。若日后 GitHub 可达、补装 Foundry，可再补 `forge script` 作为对照，不影响本实现。

## 5. 本轮回填（DoD ① 验收的两个实现 bug）

全量测试初跑时 P8 有 3 项失败（单独跑 p8 文件时 24 passing，全量套件才暴露），已修复：

1. **`asSlot` 误去前导零**：地址形如 `0x07…` 被截成 `71586…`，与运行时字节码里保留完整 20 字节的链接槽不符。改为只去 `0x`、保留 40 位十六进制。
2. **地址确定性假定 nonce 从 0 开始**：全量套件中其他文件已消耗 `signers[0]` 的 nonce，PoseidonT3 落点高于 0。`deployAll` 现显式记录 `deployNonce0` 并写入产物，测试直接据此断言，不再盲搜。
3. **确定性门禁找不到 CLI**：脚本按「仓库根调用」假设 `resolve(cwd,'contracts')`，但 `npm run` 的 cwd 已是 `contracts/`，导致路径错成 `contracts/contracts`。改为按「含 `node_modules/hardhat` 的目录」自动识别。
