## 4. 环境阻塞与替代方案（L2：Slither 不可本地安装）

### 4.1 失败过程与根因

**结论：Slither 无法在本机安装。** 根因不是网络，而是宿主对删除操作的 fail-closed 策略。

| 尝试 | 命令 | 结果 |
| --- | --- | --- |
| 1 | 在已有 venv 中 `pip install slither-analyzer` | ❌ `SAFE_DELETE_FAIL_CLOSED`，目标 `site-packages/docs/Makefile` |
| 2 | 在**全新 venv** 中安装（无历史文件可覆盖） | ❌ 同样错误 —— 排除"残留文件"假设 |
| 3 | **关闭沙箱隔离**重试 | ❌ 同样错误 —— 说明该策略在沙箱开关之上，不可绕过 |
| 4 | `--ignore-installed` | ❌ 错误目标变为 `site-packages/ckzg.cp313-win_amd64.pyd` |
| 5 | `--target <dir>`（完全绕开 site-packages） | ❌ 静默失败，目标目录未创建 |

**根本原因**：pip 安装流程必然包含文件替换/清理动作，而宿主 `SAFE_DELETE_FAIL_CLOSED` 拦截一切删除。该机制**先于沙箱隔离生效**，因此 `dangerouslyDisableSandbox` 无效。

### 4.2 替代方案与分工

| 环境 | 工具 | 用途 |
| --- | --- | --- |
| **本机（Windows 沙箱）** | **solhint**（npm 分发，可安装） | 本地快速反馈：语法、安全反模式、gas 反模式、NatSpec 完整性 |
| **CI（Linux Runner）** | **Slither**（pip 分发，可安装） | 数据流分析、重入/权限/未初始化等深度检查，`--fail-medium` |

> **参数名勘误（CI #1/#2 实测）**：`--fail-on medium` **不是** Slither 的合法 CLI 选项——
> 带值的 `fail_on` 只能写在 `slither.config.json` 里；命令行的对应开关是无值的 `--fail-medium`。
> 写成 `--fail-on medium` 会让 argparse 报 `unrecognized arguments` 并**以退出码 2 结束**
> （本机已用同一份 Slither 源码复现：同一条命令 `EXIT=2`，无任何分析输出）。
> Slither 自身「发现 High/Medium」时的退出码是 `-1`（shell 中为 **255**），通过是 **0**，
> 因此**退出码 2 一定是命令行/参数层错误，而不是扫描结论**。


CI 配置见 `.github/workflows/ci.yml` 的 `slither` job；本地以 `npm run lint:sol` 作为对应门禁。

> **风险提示**：Slither 在 CI 中的实际运行结果**本机无法验证**。首次接入 CI 时需留出调参时间（误报过滤），不应假定一次通过。

### 4.3 solhint 告警收敛过程

首次运行：**0 error / 79 warning**。收敛策略：

| 措施 | 处理 | 说明 |
| --- | --- | --- |
| `use-natspec` 缺失 `@param` / `@return` / `@author` | **补齐**（34 处） | 公开库 API 的 NatSpec 对审计方有实际价值，不应关闭规则 |
| `use-natspec` 命中测试夹具（45 处） | **通过 `.solhintignore` 排除 `contracts/harness/`** | 夹具是测试替身，不部署上链，不适用生产级 NatSpec 要求 |
| `gas-strict-inequalities`（2 处） | **显式关闭** | 该规则建议把 `<` 改为 `<=` 以省一个 opcode，但会**改变语义**。本项目选择正确性而非 3 gas |

> **注意**：`.solhintignore` **不**作用于硬约束守卫测试——`contracts/harness/` 同样受全部禁用项扫描约束。

## 5. 硬约束守卫测试（P1 核心新增）

### 5.1 设计动机

项目有多条硬约束是**「不要做什么」**：无暂停权、无 selfdestruct、无 delegatecall、不得用 `tx.origin` 鉴权、必须用 custom error 而非 `require` 字符串。这类约束在代码评审中极易漏掉，且往往到审计阶段才被发现。

**把这些「不要」写成源码扫描断言，任何违反都会在 CI 立即失败。**

### 5.2 规则清单

| 编号 | 规则 | 依据 |
| --- | --- | --- |
| HC-10 | 禁止 `PAUSER_ROLE` / `PAUSE_ROLE` / `GUARDIAN_ROLE` / `EMERGENCY_ROLE` / `HALTER_ROLE` | **冻结 Q4** |
| HC-10b | 禁止 `whenNotPaused` / `whenPaused` / `function pause\|unpause\|setPaused\|halt` | 冻结 Q4 |
| HC-11 | 禁止继承 OpenZeppelin `Pausable` | 冻结 Q4 |
| HC-12 | 禁止 `selfdestruct` / `suicide` | 上线清单 |
| HC-13 | 禁止 `delegatecall` | 不可升级决策 |
| HC-14 | 禁止 `tx.origin` 鉴权 | EVM 安全基线 |
| HC-15 | 禁止 `require(cond, "msg")` | 优化点 G7 |
| HC-16 | 禁止内联 `assembly` | 降低审计面 |

### 5.3 关键设计：注释剥离与自检

扫描前会**剥离 Solidity 注释**，因此**在注释里讨论这些禁用项是允许的**——这很重要，因为 `Roles.sol` 与 `ChainVoteAccessControl.sol` 需要明确记录「为什么没有暂停权」。

为防止注释剥离误伤代码导致规则**静默失效**，测试内含一条自检用例：注入 `function pause() external { } // PAUSER_ROLE 说明`，断言代码部分被检出、注释部分被剥离。**没有这条自检，整个守卫文件可能是空转的。**

## 6. 过程中发现并修复的 4 个工具链陷阱

### 陷阱 1 · `prettier-plugin-solidity` v2 的 parser 改名（导致格式化门禁完全不可用）

| 项 | 内容 |
| --- | --- |
| 现象 | `prettier --check "contracts/**/*.sol"` 报 `[error] Couldn't resolve parser "solidity-parse".` |
| 根因 | **v2 把 parser 名从 `solidity-parse` 改为 `slang`**（v1 的写法在 v2 直接失效）。确认方式：`import('prettier-plugin-solidity')` 后读取 `parsers` 键 → `['slang','antlr']` |
| 修复 | `.prettierrc.json` 中 `"parser": "slang"` |

### 陷阱 2 · 块注释中写 glob 路径会提前终止注释（导致 TS 编译失败）

| 项 | 内容 |
| --- | --- |
| 现象 | 测试文件报 20+ 条 TS 语法错误（`TS1109` / `TS1127` / `TS1161`），但报错行看起来都是注释 |
| 根因 | 注释中写了 `contracts/contracts/**/*.sol`，其中的 `*/` **提前关闭了块注释**，后续文本被当作代码解析 |
| 修复 | 改写为「contracts/contracts 目录下的全部 .sol 文件」 |
| **通用教训** | 在任何语言的块注释里写 glob 或正则时，必须检查是否含 `*/`。这是 LLM 生成文档时的高频错误，且报错位置与真实原因相距甚远 |

### 陷阱 3 · optimizer 导致覆盖率假阴性（★ 影响门禁可信度）

| 项 | 内容 |
| --- | --- |
| 现象 | 覆盖率报告显示 3 处「未覆盖行」（`BallotCodec:19`、`Params:84`、`Params:118`），但这些代码**都被通过测试实际执行过** |
| 定位 | 用**关闭 optimizer 的对照实验**：同一份代码，optimizer 开启时出现 3 处虚假缺口，关闭后完全消失 |
| 根因 | optimizer 将 library 的 `internal` 函数**内联**进调用方，导致 solidity-coverage 的源码映射偏移 |
| 影响 | 若不处理，覆盖率门禁会产生**假阴性**——团队追查不存在的缺口，或反向掩盖真实缺口 |
| 修复 | 新增 `COVERAGE_MODE` 开关：覆盖率采集时关闭 optimizer，gas 测量与生产部署仍用 `enabled / runs=200`。修复后行覆盖 **100%** |
| **通用教训** | 覆盖率数字必须与「测试是否真的执行了那段代码」交叉验证。仅看百分比无法发现插桩偏差 |

### 陷阱 4 · 路径分隔符导致过滤静默失效

| 项 | 内容 |
| --- | --- |
| 现象 | 缺口报告仍列出 `contracts/harness/BallotCodecHarness.sol`，而脚本明明有 `file.includes("harness/")` 过滤 |
| 根因 | Windows 下 coverage.json 的键使用**反斜杠**（`contracts\harness\...`），`includes("harness/")` 永不命中 |
| 修复 | 先归一路径再判断 |
| **通用教训** | 任何按路径过滤的脚本，读取外部工具产物前必须先归一化分隔符，否则过滤条件静默失效（不报错，只是不生效） |

### 附：还发现一处死代码

`Roles.count()` 从未被任何合约或测试调用。**处置：不是删除，而是让它变得有意义** —— 新增 `ChainVoteAccessControl.roleCount()` 并添加一致性测试 `roleCount() === roleMatrix().length`，把「新增角色时必须手工同步两处」这个易错点变成机械检查。

## 7. 角色体系设计要点

| 设计点 | 决策 | 理由 |
| --- | --- | --- |
| 角色数量 | **仅 2 个**：`CREATOR_ROLE`、`REGISTRAR_ROLE` | 权限面最小化。未使用的角色是纯粹的攻击面 |
| 审计者 / 观察员 | **不设链上角色** | 只读访问（`view` + 事件订阅）本身不受权限控制。为只读用途创建角色会制造出可被误授予、却无实际用途的权限面 |
| 部署者 | 仅授予 `DEFAULT_ADMIN_ROLE`，**不授予任何业务角色** | 支撑 P8 的「部署者无业务权限」DoD |
| `REGISTRAR_ROLE` | 标注为**风险最高的角色**，并在注释中写明「必须用 `block.timestamp < registrationEnd` 判断，禁用 `phase()`」 | 该角色决定谁能投票；F-01 已证明误用 `phase()` 会导致名册篡改窗口 |
| 暂停能力 | **不存在**（`hasPauseCapability()` 恒 false） | 冻结 Q4。该函数的存在本身是**审计信号**：若未来有人误引入 `Pausable`，此处会被一并修改，从而在评审中暴露 |
| 权限变更 | 全部通过 OZ 的 `RoleGranted` / `RoleRevoked` 事件留痕 | 支撑 R4 权限泄漏监控（测试已覆盖） |
