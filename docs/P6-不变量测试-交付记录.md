# P6 交付记录 —— 不变量与状态机随机测试（路径 A）

> 阶段：P6（原定「`forge invariant`」，因 Foundry 不可用改为**自研路径 A**）
> 日期：2026-09-18
> 结论：**自研引擎可替代 `forge invariant` 的大部分能力**，INV-1 ~ INV-10 在
> 512×64 = 32768 次随机动作下无破坏。本轮并**发现并修正了一处使随机测试形同虚设的设计缺陷**。

| **路径 A：Hardhat + 自研状态机随机测试** | ✅ **P1 决策，本阶段落地** |

### 能力差距（如实标注，不做等价性声称）

| 维度 | `forge invariant` | 本引擎 | 补强手段 |
| --- | --- | --- | --- |
| 输入层 | EVM 字节码层模糊，**能构造畸形 calldata** | ethers 层构造**合法 ABI** 调用，无法覆盖畸形输入 | ✅ **已补**：`p6b` 绕过 ethers 编码器，直接 `sendTransaction({data: rawBytes+junk})` 发原始字节（24 tests）。闭合 ERC-2771 式隐藏信道 |
| 状态断言 | 链上状态 | 链上 **+ 链下追踪**（可断言两者一致性） | — |
| 收缩（shrinking） | 自动最小化反例 | 原：❌ 无，靠 seed 复现完整序列后人工定位 | ✅ **已补**：`minimizer.ts` 窗口内贪心删除式收缩 + `finalVerified` 自验证（见 §3.4） |
| 运行速度 | 原生，快 | 每动作含一笔交易 + 10 条断言，约 16ms | — |

> **本阶段（收尾）已把两项能力缺口都补齐**：畸形 calldata（路径 B：字节码层原始发送）与
> 收缩（路径 C：确定性最小化器）。二者均以独立测试承载，不影响主战役的确定性。

**两项补偿设计**（针对上表的前两行）：
1. **链下追踪**：多条不变量（INV-1/3/4/8）无法仅凭链上查询验证——合约刻意不暴露
   「nullifier → 承诺」映射（那会泄露关联，见 P5 匿名设计）。本引擎同时掌握两侧信息，
   可断言「链上计数 == 链下记录」，这是纯模糊测试做不到的。
2. **对抗性动作为一等公民**：把「合约必须拒绝」写成可断言的 `mustRevert` 动作集
   （越权 / 伪造票据 / 重复提交 / 非法时序共 9 个），
   把「防护存在」从「有测试覆盖」升级为「每次战役中必然被触发且必然失败」。

## 2. ★★ 本轮最重要的发现：随机测试的「覆盖度陷阱」

### 2.1 现象

首版引擎跑完 512×64 = 32768 次动作，**测试全绿**。但动作统计暴露了问题：

```
finalize(重复)          revert 12317   ← 必然失败的重复调用
freezeVotersRoot(重复)  revert 15285   ← 同上
noop                    ok      5131
registerVoters          ok         2
castVote(诚实)          ok        10
reveal(诚实)            ok         3
finalize                ok         1

阶段分布: FINALIZED 32725 / 32768
```

**32768 次动作里 99.9% 发生在已封存的提案上。** 真正有价值的动作只有两位数——
**整个战役只覆盖了一个提案的一次生命周期。**

### 2.2 根因

流程一旦 `FINALIZED`，几乎所有动作的权重都变成 0（时序不再满足），
只剩「重复调用」（必然 revert）与 `noop`。序列在终态上无限空转，
而测试**依然是绿色的**——因为每条不变量在终态上本来就恒成立。

**这类缺陷极其隐蔽**：它不产生任何失败信号，只会让「跑了 32768 次」这个数字
变得毫无意义。若不做动作分布统计，永远不会发现。

### 2.3 修正

新增 `spawnLifecycle` 动作：部署全新的一组 `VoterRegistry` + `Proposal`，
切换世界引用并重置全部追踪状态（含 `maxPhase`，否则新提案的 `phase=0`
会被 INV-5 误判为「阶段回退」）。

同时收紧两个「重复」动作的适用条件——原先把它们限制在
「已冻结但未封存」的窗口内，封存后权重归零。

### 2.4 修正前后对比（同一 seed，同一规模）

| 指标 | 修正前 | 修正后 | 倍数 |
| --- | --- | --- | --- |
| 覆盖生命周期 | 1 | **887** | 887× |
| `registerVoters` 成功 | 2 | **2725** | 1363× |
| `castVote(诚实)` 成功 | 10 | **3652** | 365× |
| `reveal(诚实)` 成功 | 3 | **1528** | 509× |
| `finalize` 成功 | 1 | **886** | 886× |
| 空转占比（noop + 重复调用） | 99.9% | **10.2%** | — |
| 耗时 | 8m34s | 8m34s | 几乎相同 |

### 2.5 沉淀

**新增断言：`lifecycleCount > 3`（默认规模）/ `> 10`（完整规模）。**

这条断言的价值不在于它检查什么，而在于**它让「覆盖度是假的」这件事无法悄悄发生**。
配套的「覆盖度」统计块（生命周期 / 累计登记 / 累计票据 / 累计揭示）也是为此存在。

> **通用教训**：随机测试必须统计并断言**动作分布**与**状态覆盖**，
> 否则「跑了 N 次」与「覆盖了 N 种状态」之间的差距可以大到 887 倍。

### 3.2 不变量清单（INV-1 ~ INV-10）

| 编号 | 内容 | 检查方式 | 增量 |
| --- | --- | --- | --- |
| INV-1 | 票数守恒 | `totalMarks` == 链下 popcount 累加；封存后 `sum(counts)` == `totalMarks`；**未封存时 `getCounts()` 必须 revert** | ✅ |
| INV-2 | 揭示不超额 | `revealedCount ≤ nullifierCount`，且两者均与链下一致 | — |
| INV-3 | 一人一票 | 链下 nullifier 去重 + 链上 `isNullifierUsed` 核对 + `nullifierCount` 比对 | ✅ |
| INV-4 | 选项合法 | 已接受位图不越界、不超 `maxChoices`；`rejectedCount` 与链下一致 | ✅ |
| INV-5 | 阶段单调 | 记录 `maxPhase`，断言不回退（**有副作用，刻意为之**） | — |
| INV-6 | 封存不可逆 | `finalizeOkCount ≤ 1`；封存后 `counts` 与 `resultHash` 恒定 | — |
| INV-7 | 名册冻结 | `registrationEnd` 后 `currentRoot` 不变；`frozenRoot` 一旦设定不变 | — |
| INV-8 | 提交有效性（F-02） | 被接受的承诺必须 `isCommitmentCast == true`（双向） | ✅ |
| INV-9 | 写入滞后（F-05） | 验证失败的 nullifier 必须**未**被标记为已使用 | ✅ |
| INV-10 | 事件不含发送者（P5） | 投票/揭示/封存事件的 ABI 参数中不含 `address` 类型 | 缓存 |

**INV-1 的设计说明**：`getCounts()` 在未封存时被设计为 revert（硬约束 3 分步公示）。
若断言写成 `if (finalized) { 检查 }`，未封存期间它就是个空操作，「每轮无条件调用」失去意义。
改为「未封存时断言它必须 revert」——同一条断言在所有状态下都有实质内容，
且顺带守护了那条门禁设计。

**INV-10 的来源**：P5 实测证伪 ERC-2771 后新增。它从 ABI 层面杜绝「合约顺手记录
`msg.sender`」的可能；交易层面的「calldata 不含地址」由 `p5.metatx.test.ts` 动态验证。

### 3.3 动作集（19 个，覆盖 5 个状态变更入口）

| 类别 | 动作 | kind |
| --- | --- | --- |
| 登记 | `registerVoters` / `registerVoters(越权)` | legal / mustRevert |
| 冻结 | `freezeVotersRoot` / `freezeVotersRoot(重复)` | legal / mustRevert |
| 投票 | `castVote(诚实)` / `(已登记地址直投)` / `(重复 nullifier)` / `(错误 scope)` / `(错误根)` | legal / mustRevert ×4 |
| 揭示 | `reveal(诚实)` / `(伪造承诺)` / `(重复)` / `(时序非法)` | legal / mustRevert ×3 |
| 封存 | `finalize` / `(重复)` / `(时序非法)` | legal / mustRevert ×2 |
| 流程 | `spawnLifecycle(重启提案)` / `advanceTime` / `noop` | legal |

**权重而非等权**是必需设计：等权会让大半动作浪费在必然 revert 的调用上，
几万次仍可能没走到后半段流程。

### 3.4 ★ 失败最小化器（补上「无收缩」能力缺口）

文件：`test/invariant/minimizer.ts` + `test/p6c.minimizer.test.ts`。

`forge invariant` 失败时会自动把反例收缩到最短序列；自研引擎原本只能复现
完整 32768 步后人工定位。本模块以**窗口内贪心删除**补齐该能力。

**为什么不能直接套 ddmin**：经典 ddmin 假设「任意子集仍能触发失败」，但状态机动作有
前置依赖（删掉 `freezeVotersRoot` 后续 `castVote` 会因根未冻结而失败，bug 不再触发）。
故只能删「删掉后失败仍能复现」的动作。

**三个使最小化可行的硬前提（缺一不可）**：
1. **每步独立派生 rng**：`mulberry32(seed ^ globalStep*0x9e3779b9)`。若共享 rng 流，
   删一个动作会让后续动作拿到错位的随机值、参数全变、失败不再复现。
2. **序列可记录**：`stats.actionSequence` 完整记录。
3. **链上 + 链下一起回滚**：`snapshot`/`revert` 配 `captureTracking`/`applyTracking`——
   只回滚 EVM 会让 `nextNullifier()` 计数器继续递增，重放票据参数错位、失败不复现。

**★ 两个自救式自检（杜绝静默产出错误结果）**：
- **重放确定性自检**：首轮对完整窗口连续检查两次，结果不同则**直接放弃**并提示
  「某状态未被回滚」——否则贪心依据的「删除后仍能复现」只是随机结果。
- **`finalVerified`**：贪心循环结束后，**再验证一次**最终序列确实仍能复现失败，
  而非仅由「最后一次成功删除」推断（最后一次成功删除之后可能还有失败尝试）。

**★ 本轮实测踩到的关键 bug（已修）**：`applyTracking` 原是 `Object.assign(w, snap)`，
把快照引用拷回 `w`；但动作运行时会 `w.castedBallots.push(...)`、`w.checks.*++` 等**就地修改**
这些对象，于是**第一次重放就污染了快照**，后续 `applyWorld` 复位到含残留票据的错误状态——
表现为「同一序列首轮复现 `true`、最终自验证 `false`」的非确定性。修复：`applyTracking`
改为 `Object.assign(w, structuredClone(snap))`，每次 apply 取全新副本、`worldSnap` 永为只读。
（归类：**引用共享导致快照被回放就地修改**，是 EVM+链下双回滚最易踩的坑。）

**验证**（`p6c`）：注入合成不变量 INV-SYNTH（第 1 次 reveal 即破坏），断言
「收缩后保留 `registerVoters`+`freezeVotersRoot` 各 1 次、删除 `noop`、恰好 1 次
`castVote`+`reveal`、且 `finalVerified === true`」。修复前 failing，修复后 passing。

### 3.5 ★ 畸形 calldata 模糊（补上「输入空间」能力缺口）

文件：`test/invariant/calldata-fuzz.ts` + `test/p6b.calldata-fuzz.test.ts`（24 项）。

ethers 层只能构造**合法 ABI** 调用，覆盖不到字节码层输入空间。本模块**绕过 ethers 编码器**，
用 `provider.sendTransaction({ data: rawBytes + appendedJunk })` 直接发送原始字节，
证明「尾随的垃圾数据不改变合约行为」——闭合 ERC-2771 式隐藏信道（P5 已证伪 ERC-2771，
此处从字节码层再确认「calldata 尾随数据无害」）。

## 4. 三条硬约束的落实

| 硬约束 | 落实方式 | 验证 |
| --- | --- | --- |
| **7** 固定并打印 seed | `resolveSeed()` 默认常量 `0xc0ffee`，`INV_SEED` 可覆盖；战役开头打印 seed 与复现命令；**所有失败信息内嵌 seed + round + step + 动作名 + 复现命令** | 「相同 seed 必须产生完全相同的动作序列」用例 |
| **8** 具名断言 + 每轮无条件调用 | 10 个具名 `checkXxx` 函数；`assertAll` 在**每次动作后**调用全部 | 断言「每条不变量检查次数 == 动作总数」（实测 32768 == 32768）；另断言清单长度为 10 且 id 连续 |
| **9** 覆盖全部入口 + 非法时序/越权 | 19 个动作含 5 入口 + 9 对抗性 | 断言「每个阶段都被访问」「5 入口均成功过」「对抗性动作均被触发过」 |

**自检用例的必要性**：硬约束 8 的两条断言（清单长度、检查次数）是本轮
「覆盖度陷阱」之外的另一道防线——没有它们，有人误删一条断言或加个 `early-return`，
测试仍会全绿而覆盖已悄悄缩水。
