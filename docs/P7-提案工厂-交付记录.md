## 3. 关键设计决策

### 3.1 编号由工厂统一分配，不接受调用方传入
`createProposal` 强制 `init.proposalId == 0`，否则 `revert ProposalIdMustBeZero()`，
随后 `proposalId = ++proposalCount` 自增分配。编号是结果哈希与索引器关联提案的键，
允许外部指定会让两个提案撞号，使「提案 ↔ 结果」映射出现歧义——故以 fail-closed 拒绝非零编号。

### 3.2 提案初始管理员由工厂冻结（`PROPOSAL_ADMIN` immutable）
工厂构造时 `PROPOSAL_ADMIN = initialAdmin`（生产环境为 Timelock）。若允许每次创建时指定管理员，
则创建权限会隐含「指定任意管理员」的越权能力。工厂只负责「生」，不负责「养」——
合约不含任何暂停 / 修改 / 删除提案的接口（冻结 Q4）。

### 3.3 创建计数与索引数组恒等（INV-11）
`proposalCount`（计数）与 `_proposals.length`（索引）每次成功创建同步 +1，恒等是一条链上不变量。
第 i 个下标（0 起）对应编号 i+1，故 `proposalOf(i+1) == proposalAt(i)`。
INV-11 每轮动作后无条件调用，仅查**边界**（最近一次创建）即可在新提案写入时即发现回归——
工厂 append-only，全表遍历在 512×64 战役下复杂度会膨胀到 O(动作×提案)，边界检查是性能与守护强度的平衡。

### 3.4 内联 `Proposal` 创建码的体积（★P7 最关键的工程冲突）
`new Proposal(...)` 把 `Proposal` 的**创建字节码**内联进工厂运行时代码。实测体积：

| 构建 | Proposal 创建码 | Proposal runtime | Factory runtime |
| --- | --- | --- | --- |
| optimizer ON（生产） | ~9.96 KB | ~8.08 KB | **13.37 KB（54.4%）** |
| optimizer OFF（覆盖率） | ~25.24 KB | ~18.98 KB | ~27 KB（超限） |

EIP-170 上限 24 KiB。生产构建下工厂远低于上限，**真实可部署**；但覆盖率构建关闭 optimizer 后
工厂运行时代码膨胀到 ~27 KB，会触发 EIP-170，`new Proposal` 在覆盖率网络下直接 revert，
导致 P6 不变量测试与 P7 单测在覆盖率模式无法部署工厂。

**解决（双保险，二者不冲突）：**
- `hardhat.config.ts`：覆盖率模式下 `allowUnlimitedContractSize: COVERAGE_MODE`（仅测试网络放开，
  使覆盖率采集能部署工厂；生产部署仍受真实上限约束）。
- `ci.yml`：把**体积 / 链接门禁移到 `coverage` 之前**，使其基于 optimizer 开启的生产字节码；
  覆盖率插桩产生的膨胀是工具产物、并非可部署形态，不应污染 EIP-170 门禁。

> 注：`check-link-references.mjs` 也扫描 oversized 合约，故同样需在 coverage 前、基于生产字节码运行。
